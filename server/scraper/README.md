# lineup-scraper（出題データ自動更新 Cloud Run Job）

タカラトミー公式 [BEYBLADE X ラインナップページ](https://beyblade.takaratomy.co.jp/beyblade-x/lineup/index.html) から新商品を検知し、GCS上の出題データ `beyblades.json` を**完全自動**で更新する。週1回 Cloud Scheduler から起動する想定。

設計原則: **疑わしきは更新しない**。分解できない商品名・画像死活NG・安全弁違反はすべて登録を見送り、通知に列挙するだけに留める（現行データ維持）。

## 処理フロー

1. 現行データ取得（GCS `DATA_BUCKET`/`beyblades.json`、または `SEED_PATH` のローカルJSON）
2. ラインナップページ取得（User-Agent: `beyblade-x-quiz-bot/1.0 (personal fan project)`、全リクエスト1秒以上間隔）
3. `ul.lineupList li` から商品コード・商品名・カテゴリ・詳細slugを抽出
4. ベイ本体判定（除外ルール）→ 商品名分解 → 追加候補アイテム生成
5. 新規アイテムの画像URLをHEADで死活確認（200かつ `image/*` のみ採用）
6. 安全弁を全通過したらGCSへアップロード → 通知

## 環境変数

| 変数 | 必須 | 説明 |
|---|---|---|
| `DATA_BUCKET` | 本番◯ | 出題データを置くGCSバケット名 |
| `DATA_OBJECT` | − | オブジェクト名（既定 `beyblades.json`） |
| `SEED_PATH` | − | 現行データをローカルJSONから読む（指定時はGCS読み込みをスキップ。DRY_RUN動作確認用） |
| `DRY_RUN` | − | `1` でアップロードなし。差分と判定結果をstdoutへ整形出力 |
| `SLACK_WEBHOOK_URL` | − | あればサマリをPOST。無くてもstdoutへサマリJSONを常時出力（Cloud Logging行き） |
| `LINEUP_URL` | − | 取得先の上書き（テスト用） |
| `REQUEST_INTERVAL_MS` | − | リクエスト間隔（既定・下限 1000ms） |
| `REQUEST_TIMEOUT_MS` | − | HTTPタイムアウト（既定 15000ms） |

GCSへの書き込みは Cloud Run Job のサービスアカウント（ADC）を使用。ローカルで本番相当を動かす場合は `gcloud auth application-default login` が必要。

## 実行

```bash
cd server/scraper
npm ci

# テスト（分解ルールのグラウンドトゥルース35件・抽出・安全弁）
npm test

# ローカルDRY_RUN（GCS不要・アップロードなし）
SEED_PATH=../../data/beyblades.json DRY_RUN=1 npm start

# 本番相当
DATA_BUCKET=<bucket> npm start
```

終了コード: 正常（更新あり/更新なし）= 0、安全弁違反・エラー = 1。

## 商品名の分解ルール

- 標準形: `<ブレード名><ラチェット><ビット>`（例 `ドランソード3-60F`）
- CX系: `<ブレード名><アシストブレード英字1〜2><ラチェット><ビット>`（例 `ドランブレイブS6-60V` → ブレード「ドランブレイブ」）
- ラチェット: `X-NN`（Xは数字1桁または英大文字1文字、NNは数字2桁。例 `3-60`, `M-85`）
- ビット: 末尾の英字1〜3文字（例 `F`, `GF`, `WW`, `LR`）
- 一体型（ラチェット表記なし。例 `バレットグリフォンH`）はブレードのみ登録
- ブレード名は純粋な和文であること（ASCII混在は分解不能として弾く。ダブルスターター対策）
- 全角英数字・各種ハイフン・空白は正規化して吸収
- **分解できない商品名は登録せず、通知に列挙**

`data/beyblades.json` の全35ブレードが正しく分解できることを `test/parse.test.js` がグラウンドトゥルースとして保証する。

## 除外ルール（ベイ本体でない商品）

- キーワード: スタジアム / ランチャー / ワインダー / ケース / バトルパス / カスタマイズ・カスタム / ランダムブースター / セット / グリップ / ステッカー / エンブレム / パッケージ
- カテゴリがスターター・ブースター以外（ツール、セット、ランダムブースター、ダブルスターター等）。**未知のカテゴリも保守的に除外**
- 限定・特殊流通品: コード `BX-00`/`UX-00`/`CX-00`（コードが一意でなく画像URL規約が適用できない）、商品名に `【…】` や「限定」を含むもの
- 除外した商品もすべて通知に列挙する（見落とし検知のため）

## アイテム生成

- スキーマは `docs/architecture.md` の通り。画像URLは `_image/<コードのハイフン無し>_<index>@1.png`（`01`=ブレード, `03`=ラチェット, `04`=ビット）
- 既存データが大文字（`BX01_01@1.png`）を使っているため大文字を第一候補、docs記載の小文字を第二候補としてHEADで死活確認し、通ったURLを採用
- ラチェットは名前で、ビットは英字キーでユニーク（既存にあれば追加しない）。ブレードも同名の再録・色替え（例 BX-05 はBX-03と同内容のブースター）は追加しない
- ビット名称辞書（F=フラット 〜 GN=ギヤニードル）に無いビットは英字そのまま登録し、通知で辞書追加（`src/bits.js`）を促す

## 安全弁（`src/validate.js`）

1. スキーマ検証: 全アイテムが必須フィールド・形式を満たす（id一意含む）
2. 件数ガード: 新データ件数 >= 現行件数、増加は+20件以内
3. 現行アイテムの欠落（すり替わり）が無いこと — 追加のみを許可
4. 違反時はアップロードせずエラー通知して終了コード1

## 通知

- stdoutへ `{"scraperSummary": {...}}` を常時出力（新規 / スキップ / 除外 / 画像NG / 辞書未登録ビット / 違反 / エラー）
- `SLACK_WEBHOOK_URL` があれば整形テキストをPOST

## 運用上の注意（サイト構造変更時の壊れ方と検知）

| 変化 | 挙動 |
|---|---|
| ページ全面改修で `ul.lineupList` が消える | 抽出0件 → 「サイト構造変更の疑い」エラーで終了コード1（誤って更新しない） |
| li内の `<b>コード<span>名前</span></b>` 構造が変わる | 抽出0件または大幅減。0件ならエラー。部分的に壊れた場合も**追加のみ**なので既存データは壊れない |
| 商品名の命名規則が変わる | 分解不能 → スキップとして通知に列挙（登録されない） |
| 新カテゴリの登場 | 保守的に除外し、除外理由付きで通知に列挙 |
| 画像URL規約の変更 | HEAD失敗 → そのアイテムのみ未登録、通知に列挙 |
| ページ自体が404/タイムアウト | エラー通知して終了コード1 |

- 週次実行で `status: blocked / error` の通知が来たら `test/fixtures/lineup.html` を実ページで取り直し、`extract.js` / `parse.js` を修正してテストを更新する
- 本ジョブは既存アイテムの削除・変更を一切行わない。名称修正・削除が必要な場合はGCSオブジェクトを手動更新する
- リクエストは毎回: ページ1回＋新規アイテム数×HEAD 1〜2回のみ。すべて1秒以上間隔
